## 0. 约束映射（把原题换成本项目）

| 原题约束 | 本项目对应 |
| --- | --- |
| 后端 FastAPI（异步）Python 3.11+ | 保留。异步用于 TMS/GPS 轮询、LLM 调用与工作台并发，不用来掩盖串行业务 |
| LLM 走 API、供应商可替换 | 保留。抽象 LLM Adapter，默认 OpenAI 兼容协议；敏感字段脱敏后出域，允许降级本地模型 |
| 知识库：报销制度文档 | 本项目 = **异常处置规则、承运商 ETA 口径、签收与回执规范、人工接管红线、话术模板**，按版本与生效日期检索 |
| 两个角色：员工 / 管理员 | 前台仍是**两类使用者**：一线业务用户（调度、客服）/ 管理员（运输负责人、合规）。但内部必须落到**运单级 ABAC**，不能用两个大角色糊过去 |
| 员工问答 + 发起报销 | 本项目 = **查单问答 + 异常上报 + 生成回复草稿 + 发起交接**；不产生对外发送动作 |
| 管理员维护知识库 + 看记录 | 本项目 = **维护规则/口径版本 + 审核草稿 + 查看接管与审计记录** |

**明确不做**：不写回 TMS、不下发路线、不自动判责扣罚、不直接对客户发消息、不让 LLM 决定接管。

## 1. 四层架构（文字版）

```
┌───────────────────────────────────────────────────────────────┐
│ L1 入口层                                                     │
│  · 业务工作台（调度/客服）：查单、异常上报、草稿审核、待办      │
│  · 管理后台：规则与口径版本、知识库、授权、接管与审计           │
│  · 系统入口：TMS 只读适配器（5min 轮询）、GPS 轨迹、IM 留痕(可选)│
│  · 鉴权：企业 SSO/OIDC → 运单级 ABAC → 字段级白名单            │
├───────────────────────────────────────────────────────────────┤
│ L2 服务层（领域服务，全部幂等）                                │
│  运单映射 · 事件归一 · 证据包 · 待办路由 · 草稿审核             │
│  人工接管 · 知识检索 · 反馈闭环 · 审计 · 指标                  │
│  ↑ 对外只暴露「只读查询」与「内部待办」，没有 TMS 写通道        │
├───────────────────────────────────────────────────────────────┤
│ L3 智能体编排层                                               │
│  意图路由 → 工具调用（只读）→ 证据检索 → 结构化生成 → 护栏      │
│  · 工具白名单：get_shipment / get_track / get_events /         │
│    get_evidence / search_policy                                │
│  · 护栏：禁承诺赔付、禁输出受限字段、必须带数据时间与版本        │
│  · 闸门：红线路由与接管判定是确定性代码，LLM 无权决策           │
├───────────────────────────────────────────────────────────────┤
│ L4 数据模型层                                                 │
│  PostgreSQL：主数据 + 事件流 + 审计（append-only）+ pgvector    │
│  Redis：会话缓存、限流、任务队列                               │
│  对象存储：原始报文、轨迹快照、签收图片                        │
│  回放沙箱：DuckDB/Parquet（离线回放与指标复算，不污染主库）      │
└───────────────────────────────────────────────────────────────┘
```

**一句话数据流**：TMS/GPS 只读拉取 → 归一为带版本的事件 → 生成证据包 → LLM 产出**草稿** → 确定性闸门（红线/授权/时效）→ 人工审核或接管 → 只追加审计。

### 选型结论与替代方案

| 决策 | 选择 | 理由 | 何时换 |
| --- | --- | --- | --- |
| 部署形态 | **模块化单体**（一个后端 + 一个 worker） | 20 万预算、单干线试点，微服务只会增加运维与联调成本 | 多干线/多租户后再拆事件服务与智能体服务 |
| 数据库 | **PostgreSQL + pgvector** | 事件、映射、规则版本、向量在同一事务域，知识版本与草稿引用强一致 | chunk 超百万或检索 QPS 高时换 Qdrant |
| 事件模型 | **事件流 + 物化当前态** | 只追加、可回放；当前态查询快 | — |
| 任务调度 | FastAPI 进程外 **独立 worker + Redis 队列** | 5 分钟轮询、草稿生成不能阻塞请求 | 任务量上来换 Celery/Arq 集群 |
| LLM | **Adapter + OpenAI 兼容 + 结构化 JSON 输出** | 供应商可替换；输出可校验；失败可降级模板 | — |
| 检索 | **BM25 + 向量混合**，按线路/日期/版本过滤 | 制度类文档关键词命中比纯向量稳 | — |
| 前端 | 服务端渲染的管理后台 + 独立工作台 | 首期只求可用与可审计 | 后期再做独立前端 |

## 3. 数据库表设计

### 3.1 表清单

| # | 表 | 关键字段 | 约束 / 索引 | 用途 |
| --- | --- | --- | --- | --- |
| 1 | `users` | id, employee_no, name, persona(一线/管理员), org_id, status | unique(employee_no)；index(org_id) | 账号与身份 |
| 2 | `authorization_grants` | id, customer_id, shipment_id, field_scope, granted_by, granted_at, revoked_at | index(customer_id, shipment_id)；revoked_at 空=有效 | 运单级授权与字段白名单 |
| 3 | `sessions` | id, user_id, channel, context, started_at, last_active_at | index(user_id, last_active_at) | 会话上下文 |
| 4 | `messages` | id, session_id, role, content, intent, tool_calls, data_time, confidence, created_at | index(session_id, created_at) | 对话与工具调用留痕 |
| 5 | `shipments` | id, tms_no, customer_id, lane_id, carrier_id, plan_eta, eta_basis, status | unique(tms_no)；index(lane_id, status) | 运单当前态 |
| 6 | `waybill_map` | id, shipment_id, carrier_sub_no, carrier_id, valid_from, valid_to, source, version, confidence | unique(shipment_id, carrier_sub_no, valid_from)；index(carrier_sub_no) | 多对多映射（带有效期） |

| 8 | `evidence_snapshots` | id, subject_type, subject_id, source, data_time, version, payload_uri, hash, freshness | index(subject_type, subject_id, data_time) | 证据快照与时效 |
| 9 | `drafts` | id, session_id, shipment_id, draft_type, content, evidence_refs, confidence, status, reviewer_id, reviewed_at, model_version | index(shipment_id, status)；(reviewer_id, status) | 回复草稿与审核 |
| 10 | `handoffs` | id, event_id, from_user, to_user, due_at, return_reason, accepted_at, status | index(to_user, status, due_at) | 交接待办（接手人确认才闭环） |
| 11 | `takeovers` | id, subject_type, subject_id, reason_code, reason_text, operator_id, started_at, confirmed_at, mode, status | index(subject_id)；index(operator_id, started_at) | 人工接管 |

| 13 | `policy_rules` | id, rule_type, version, scope, effective_from, effective_to, config, status, approved_by | unique(rule_type, version)；index(scope, effective_from) | 路由/红线/时效规则版本 |
| 14 | `knowledge_documents` | id, title, doc_type, version, effective_from, effective_to, lane_scope, status, checksum, file_uri | unique(doc_type, version)；index(lane_scope, effective_from) | 制度与口径文档 |
| 15 | `knowledge_chunks` | id, doc_id, chunk_no, content, embedding, meta | index(doc_id)；向量索引(HNSW) | 检索分片 |

### 3.2 设计规则（比表结构更重要）

- **三种时间必须分开**：`event_time`（业务发生）、`received_at`（系统收到）、`data_time`（数据快照时刻）。查单答复引用的是 `data_time`，不是 `created_at`。
- **版本不覆盖**：任何修正插入新行，`version+1`，旧行保留；审计只追加。
- **幂等键**：`dedupe_key = event_no + type_code + event_time + source`，接口恢复后按业务编号去重补齐，避免重复待办。
- **不猜值**：缺主编号/事件时间/来源/版本的记录进 `exception_events` 之外的修复队列（可用 `status=needs_repair` + 独立表），不能补默认值。
- **授权在仓储层执行**：所有运单查询必须带 `authorization_grants` 过滤，不靠接口层自觉。
- **PII 最小化**：定位、电话不落 `messages.content`；只存脱敏值或引用；审计不记口令。
- **知识库检索必须带过滤**：`doc_type + lane_scope + effective_from/to`，回答必须返回引用片段与版本号。

## 4. 第一周的最小验证目标

**目标一句话：一条干线、一票贯通、二十票回放，全程不出系统。**

### 4.1 打通的金路径

```
1 份 TMS 查单样本 + 1 份异常记录
  → 适配器只读解析（不连生产库，用脱敏导出）
  → 运单↔子单映射（至少 1 组多对多样本）
  → 归一为 exception_event（四要素校验通过）
  → 组装证据包（轨迹 + 计划 + 异常 + 回执 + 版本 + 数据时间）
  → LLM 生成 1 条结构化草稿（带引用、置信度、待刷新标记）
  → 确定性闸门判定：通过 or 转人工接管
  → 客服主管审核并记录修正
  → 审计日志可重建这次处理
```

### 4.2 验收口径（第一周只认这 6 条）

| # | 验收项 | 标准 |
| --- | --- | --- |
| 1 | 样本覆盖 | 1 条干线、近 2 周、**20 票**异常样本 |
| 2 | 归一成功率 | 四要素完整率 ≥95%，缺字段全部进修复队列且可见 |
| 3 | 草稿可追溯率 | **100%** 草稿带原记录链接、`data_time`、来源、版本 |
| 4 | 人工修正 | 客服主管逐条核对，修正原因可归类（不是只改文字） |
| 5 | 接管演示 | 至少 3 类红线（赔付/危险品/紧急事故）能确定性拦截并留痕 |
| 6 | 对外动作 | **0 次**对外发送、0 次 TMS 写入 |

### 4.3 第一周明确不做

- 不接生产 TMS 实时轮询（只用脱敏导出）
- 不接 IM 群消息、不做司机端采集改造
- 不做全量知识库（只放 5–10 份核心规则/口径文档）
- 不做多干线、多租户、自动派单、自动结算
- 不做前端美化，工作台只需能用 + 能留痕

### 4.4 停止条件

- 20 票里映射错误 >2 票，或四要素缺失 >20% → 先修主数据，不进第二周
- 草稿出现「承诺赔付」或受限字段 → 立即停生成，回查护栏
- 客服主管认为草稿不可用 >50% → 问题在证据包而非模型，先补证据

## 5. 风险与架构对策

| 风险 | 架构对策 |
| --- | --- |
| 多对多映射错 → 误报放大 | 映射独立服务 + 有效期 + 人工修复队列；不用默认值 |
| 回执延迟 24h → 把未回执当未到货 | 到货/回执分离建模；`freshness` 字段；草稿强制标注数据时间 |
| LLM 越界承诺 | 生成前字段白名单，生成后规则扫描；承诺类话术走模板，不自由生成 |
| 接管语义不清 → 审计断链 | 确定性状态机；接管原因/接手人/时间必填；只读模式固定 |
| 授权撤销不生效 | `revoked_at` 生效即策略缓存失效；越权访问单独审计事件 |
| 知识过期 | 文档带有效期；检索过滤；回答必须展示生效版本 |
| 预算不够 | 模块化单体 + 单库 + 单 worker；先回放后实时 |

## 6. 待确认（影响架构，不定会返工）

1. TMS 导出样本能否脱敏提供？决定第一周能否真跑。
2. 是否存在稳定的「业务编号」用于去重（运单号还是子单号）？
3. 授权由谁授予、撤销如何生效？决定 ABAC 策略缓存与授权表结构。
4. 企业是否允许外部模型 API？决定 LLM Adapter 的默认实现与脱敏网关。
5. 签收回执是否可获取原图/拍摄时间？决定证据包能力边界。
6. 试点线路与班次由谁指定？决定 `lane_scope` 与灰度开关。
